# Open code-generation patterns (integrator notes)

## Function-local static vector: first expansion calls the constructor out of line (2026-11-18)
- Seen in Multiplayer.cpp `Game_Mode_From_ID` 0x1b3af0 (and 0x1b3bc0, 0x1b3cf0, 0x1b4d20) and in MPCoop.cpp's constructor 0x19f720.
- The original expands the `Game_Modes()` guard twice in one function. In the first expansion it calls `VectorClass<T>::VectorClass(0, 0)` out of line (0x1b6170), then stores the DynamicVectorClass vptr and its fields inline. In the second expansion it inlines the VectorClass constructor completely.
- Our build inlines both. Moving the constructor out of the class body (as in VECTOR.H) changed nothing. Function sizes are equal, so only the inlining decision differs.
- Hypotheses not yet tested:
  - VC6's per-function inline budget (`#pragma inline_recursion` / `inline_depth`);
  - the order in which the source defines the accessor and the constructor;
  - whether the original declares the accessor `inline` explicitly.

### Solved (investigation agent, 2026-11-18): VC6 per-caller inline budget
- Each calling function has an inline-size budget. It is not a call count and not an inline depth, and it grows with the caller's own code size.
  - Expansions are accepted until the budget is spent. After that, larger callees are called out of line, while tiny ones (a single store or a forwarder) are still inlined.
- Processing order: a for-loop BODY is expanded before its CONDITION. So when the budget runs out, the expansion in the condition is cut first; it is emitted first in the code.
- Wrapper cost: `return X().Count();` (one more nested inline) costs budget, while `return X().ActiveCount;` is effectively free.
- `#pragma inline_depth` only works at file scope.
- Multiplayer fix: `Game_Mode_Count()` should use `Game_Modes().Count()`, and `Default_Game_Mode` should test `Game_Modes().Count() == 0` directly. This matches 0x1b3af0 and emits 0x1b6170. The file is experiments/inline_static_vector/v_c_def_count.cpp.
- Fill_Game_Mode_Combo and Fill_Game_Mode_List need about 26-36 "probe statements" of extra inline cost from some natural construct that emits no code. That construct is not yet found.
- Gauge technique: a dead inline `Probe(n)` measures the missing budget; then look for a natural construct of that cost.

### Recurring (2026-11-18): "a dead inline probe of N statements gives a full match"
Seen in scenario 0x252810, queue 0x21b690, infantry 0x1011a0, tactical 0x2a0410, and Multiplayer Fill_Game_Mode_*.
- The original spent inline budget on code that leaves no bytes.
- Plausible natural sources still to test:
  - debug blocks under a compile-time-false constant (`if (Debug_X)` with a const false, or a `#define` to 0) whose bodies call inline helpers;
  - inline accessors whose result is unused;
  - Westwood profiling macros that expand to inline calls.
- Do NOT adopt an artificial probe into the source; record the measured probe size per function instead.

### Decision (integrator, 2026-11-18): the natural source of the missing inline budget is `assert`
- The saveload agent measured that `((void)0);` statements, which is what `assert(x)` expands to under NDEBUG, raise the caller's inline budget exactly like the dead probe.
  - Save_Game needs 23..60 of them, Put_All about 80 and Get_All about 33.
- Westwood code (TS/RA source) uses `assert()` heavily. 1.006 sources reconstructed from a different binary have none.
- Direction matters:
  - asserts make the CALLER larger, which RAISES its budget. This fits when 1.001 inlines MORE than our source (saveload).
  - When 1.001 inlines LESS than our source, something consumed budget without emitting bytes: an inline call whose body optimizes away. That natural construct is still open (no probes).
- Rule from now on:
  - Where a function matches only with extra budget (1.001 inlines more), you MAY add `assert(<meaningful condition>);` statements.
  - Use conditions such as parameter/pointer validity or index ranges, in plausible places: function entry, before dereferences, loop bodies.
  - Mark them `// level-2: assert inferred from VC6 inline budget`.
  - Prefer the smallest number of asserts that gives the exact match. Never use dead `if (0)` blocks or probe functions.
- Make sure `<assert.h>` (or the tree's own assert macro) is included and that NDEBUG is defined. NDEBUG is part of our flags.
- Review note (2026-11-18): saveload Put_All needed 274 asserts, about 5 per saved vector, which is implausibly many as hand-written lines. A more natural form is a per-vector save macro whose body holds those asserts. Refactor it later; the bytes are already proven.
- Measured gauge for the "1.001 inlines LESS" direction (ldprgmgr Draw): three dead `Is_Observer();` statements, which are inline calls with a discarded result, reproduce 1.001's inlining exactly. The natural counterpart is probably leftover inline accessor or debug-helper calls whose results are unused. Do not adopt these unless the call is plausible in context; record the gauge instead.

### `lea [a+b]` versus `[b+a]` one-byte differences (vector-order experiment, 2026-11-18)
- Source operand order (`Vector[i]`, `*(Vector+i)`, `*(i+Vector)`) makes NO difference, because VC6 normalises it.
- What decides the base/index order is how the values came into being:
  1. pointer arithmetic on an unsigned versus an int index;
  2. the order in which struct fields were created. For example, `rect.Set(x, y, w, h)` versus `rect = Rect(...)` fixed planmgr Draw_Lead_Box.
- The wdtmap WDT_Write_Map_Ini case needs unsigned pointer arithmetic in VectorCursor::operator*. The only working form found, `(&(*Vector)[0])[Cursor]`, is unnatural, so it was not adopted. house AI_Raise_Money is still open.
- Experiment files: experiments/vector_order (regress.py runs all claims of given TUs against an include dir).

### Refuted (2026-11-18): asserts inside shared helpers do not explain "1.001 inlines LESS"
- Adding asserts to a helper does raise its inline cost, but it changes every caller. No single count reproduces 1.001 in all failing callers, and every count that changes a target breaks matched functions.
  - Example: 15 asserts in the DynamicVectorClass ctor fix wave Load but cause 23 regressions.
- Conclusion: the budget effect is local to each caller. Handle these cases locally, for example a natural construct in the caller, and record the measured gauges.
- Data: experiments/helper_asserts (result_*.json, run.py, mkvar.py).

### Extension of the assert rule (integrator, 2026-11-18): "1.001 inlines LESS" via asserts in a TU-LOCAL helper
- The WinMain gauge works with dead statements inside module-local inline helpers (RegisterClasses, Init_Keys) that are expanded before the cut point. Inlining such a helper consumes the caller's budget.
- An assert inside a helper costs budget but emits nothing.
- So for a helper that is local to the TU (static or file-local, inlined only in this file), asserts in that helper are an allowed natural construct, with the same marking.
- Do NOT put asserts in shared header helpers: the helper_asserts experiment showed cross-module regressions there.

### Two compiler artefacts that explain many remaining near-misses (2026-11-18)
1. Header-count effect. The NUMBER of declarations in included headers changes VC6's register and stack choices in unrelated functions.
   - Example: 3 new SelectClass declarations in sidebar.h broke wonline Draw_Player_List and Pick_Lobby.
   - It is probably due to symbol numbering. So 1.006-only declarations left in our headers can be the reason a 1.001 function does not match.
   - Principled fix: remove 1.006-only declarations so that the header has the 1.001 member set.
2. Frame-slot order depends on local variable NAMES (WinMain experiment).
   - Renaming only `cfile` moved its slot: `fileptr` gives the original slot.
   - This fits VC6 ordering locals by a hash of their names. Many "stack slot" near-misses are therefore probably caused by different local names than the original.
   - Lead: a tool that tries plausible Westwood-style names per local and scores matching ebp/esp slots. The scratch tools are in the WinMain agent's scratchpad (startup/lay.py, mkvar.py).
- sidebar.h header-count window: wonline Draw_Player_List and Pick_Lobby match only when 3-5 of the 1.006-only declarations are removed. The chosen form removes 3: Request_Redraw, Request_Column_Redraw and Stop_Tab_Flash.
- Re-run wonline.cpp after ANY sidebar.h edit. In general: after a header edit, run the full check (not only the module) before integrating.
- CORRECTION (local-names experiment): local names decide frame slots ONLY in functions containing `__try` (SEH). In GAME.EXE that is WinMain, plus 13 library functions.
  - Rule in SEH functions: within a scope, order by the symbol-table bucket ((h<<2)+(h>>4)+ch, then (h^(h>>16))&15), ascending; later declarations first within a bucket. The outer scope comes first, then nested scopes in pre-order; temporaries go last.
  - Tool: experiments/local_names/name_search.py.
  - In normal esp-frame functions names are irrelevant. There the order comes from use weight and size, first use breaks ties, and block scopes share slots.
- Budget gauge detail (techno Draw_Health_Bar): dead `Point3D(1,2,3);`, `Point2D(1,2);` and `dim / 2;` cost nothing, because the front end discards them. Dead `Coord(1,2,3);` and inline calls DO cost budget. So the natural "inlines LESS" source is probably an unused Coord-type temporary or an unused inline call result in the original.

## Near-miss rules (Fable agent, 2026-11-19)
- Check the differing instructions of a near miss for changed IMMEDIATES before treating them as register noise. Example: Damage_Low_Bridge2_NS "7 bytes" was 5 bytes of register choice plus a real 1.001 constant (overlay 0xE8 instead of 0x142).
- `add r1,r2` versus `add r2,r1` when both registers die: source operand order, casts, named temporaries and declaration order all normalise to the same choice. Only a different way of creating the values moves it, and that reshuffles the whole function. Examples: Place_Waterfall, the inline Union compare in Damage_Low_Bridge*.
- A named local for a virtual call's argument changes the register rotation, from vptr=eax/arg=ecx to arg=eax/vptr=edx. This is a lever for wrong-register virtual-call tails (Fire_Direction).
- Raw differing-byte counts can point the wrong way. A diagnostic edit that changes ONE instruction and makes everything else identical is the better structural test (Laser_Zap: if/else is the 1.001 form, the ternary was a false lead).
- For class-returning calls, if/else `dest = A(); / dest = B();` shares one return-temporary slot and tail-merges the field copies; a ternary gives each arm its own temporary.
- VC6 reuses dead stack-argument slots as spill slots.
- Constant 0 in a register (`xor ebp,ebp` then `cmp reg,ebp` / `mov [mem],ebp`) means an int local lost its register.
- A ternary select compiles branchless (setg/dec/and); only the if form gives test/jle/xor.
- A pointer local declared before any call is forward-substituted and does not make its base a whole-function register candidate.
- In a switch-based dialog procedure, `return FALSE;` inside each case delays a callee-saved `push ebp` into the one branch that uses it. `break;` with a single return at the end saves it early, which is what GAME.EXE does (CampaignEndScore Dialog_Proc).
- One function-level variable reused across switch branches permutes spill slots; block-local variables per branch fix this. The declaration order of an int and a bool local decides their slots.
- Tail-merged calls (`name = F(); ... return name;`) mean the helper has the wrong form. An inline helper with one `return F(..)` per branch keeps the calls separate.

## KEY: inline-budget causes inside the source (Fable, 2026-11-19)
- "1.001 inlines LESS" often has a natural source: m85 wrote an inline call out as flat code. Restoring the real call, e.g. `Options.Reset_AI();` or `Set_Digest(tail);`, gives identical bytes for that code. It consumes inline budget, and the out-of-line calls elsewhere then appear by themselves. A meaningless test such as `if (tail)` on an array gives this away: it is the callee's NULL check surviving inlining.
- "1.001 inlines MORE" can come from m85's own `static inline` helpers. Writing them out as the caller's own code makes the caller larger before inlining and raises its budget. Read_Scenario_Descriptions needed 300+ asserts with the helpers and zero without them. Try this BEFORE asserts.
- VC6 inlines functions that are defined later in the same TU.
- Discarded trivial accessors cost no budget and are useless as gauges.
- Temporaries inside ONE full expression are never reused; across statements VC6 packs them by liveness. If 1.001's frame is N x sizeof(class) larger than ours, the original computed everything in one expression (Draw_Matrix: 0x224).
- In an inlined callee, the if-body's expansions get budget before the condition's.
- Gauges of 100+ identical asserts are probes, not source: such a function is NOT claimed (Drive/Ship Draw_Matrix, which needs 117). Record the count as a measurement only.
- The inline budget has TWO regimes (Fable, rules.cpp):
  - Medium-sized functions (Audio_Visual_Rules, 10.9 KB): more caller statements or asserts give MORE inlining.
  - Very large functions (General, 14 KB): the caller's size counts against a cap, so extra statements or asserts give LESS inlining, and the cost adds up per statement. In this regime asserts cannot repair a "1.001 inlines MORE" case; the source must get lighter instead.
  - General and TechnoType Read_INI both look about one call statement lighter in 1.001 with identical code. This suggests a shared header inline or declaration cost rather than the bodies.
- Two byte-identical template copies with the same callee in one TU can be the const and the non-const pointer instantiation, e.g. rules.h EMPulseSparkles/OreTwinkle are non-const AnimTypeClass*. Listing the INI key per call site identifies which.
- Tools: fable_rules scratch `sdiff.py` (instruction diff that ignores relocations and shifts) and `calls.py` (call-target histogram, ours against the original).

## KEY: explicit comparisons in header inlines cost inline budget (Fable, 2026-11-19)
- `if (x != 0)`, `== 0` and `!= NULL` in a HEADER INLINE cost VC6 more inline budget than the implicit truth test `if (x)` / `if (!x)`, although both give identical code.
- m85's headers use explicit comparisons in many inlines. Making them implicit is a cheap lever for "1.001 inlines more" near misses.
- Proof: one token in findmake.h `TGet_Class` (`Get_String(...) != 0` -> `Get_String(...)`) made RulesClass::General (14 KB) match. The full check stayed clean.
- A proposal not yet applied: ccini.h `Get_VocType` `== 0` -> `!`. It takes Audio_Visual_Rules from 287 to 26 hunks.
- Apply this only with a FULL check: it changes the budget of every caller.
- Tool: fable_hdr scratch `regress.py` (claims of the given modules against an include directory) and `scan.py` (unclaimed functions whose masked bytes now occur in GAME.EXE).

## The "inline budget" is a COUNT rule (Fable, 2026-11-19, measured on wave Load and strtable LoadFile)
- Whether a nested expansion happens depends on the NUMBER of direct inline call sites in the caller's statements AFTER it, not on their size.
  - Three one-line helpers act exactly like three helpers with a loop.
  - A helper that nests three inline calls counts as one.
  - `Ident(Ident(Ident(x)))` in one statement counts as three.
  - Sites BEFORE the statement do nothing, even 80 of them; sites nested inside other callees do nothing.
- The calls that get cut are the compiler-generated ones inside an inlined function: the member/base constructors of an inline ctor, and the local destructors of an inlined helper.
- "1.001 inlines more": remove inline call sites from LATER statements, e.g. write Point2D arithmetic flat. This fixed the XSurface ctor in Techno_Blit_Voxel, where 25 asserts did not.
- "1.001 inlines less": look for flattened inline calls only in statements AFTER the affected one, and count them.
- The choice of callee-saved register follows use counts; a single use flips it.
- `Point2D()` passed as an argument builds a temporary; the default `Point2D(0,0)` is pushed as constants.

## Lessons from wave w5 (2026-11-21, gameplay TUs)
- A redundant NULL test written by hand before an RTTI cast is a flattened inline cast helper. Restoring the helper call (for example Unit_As_Building) is the natural "1.001 inlines less" fix (unit Per_Cell_Process).
- A dead `add reg,disp` after displacement-folded member loads means 1.001 took the field by `const &` reference and copied it member by member (unit Do_MISSION_UNLOAD, RefinerySmokeOffset).
- Long INI readers in the growth regime: read each value through a typed local, then store it in the field. This extends m85's own style, so all the locals are real. It shifts inline decisions without probes (rules Audio_Visual_Rules, 11 KB). The window is narrow; measure each step.
- techtype Read_INI confirms the COUNT rule. Every real helper call site after the voice lists (Load_Palette, Has_Turret_Weapons, _Scale_To_256, Free_Image, gibbo's Read_Sound) moves exactly one later VectorClass::Clear out of line.
- A named local object passed by const reference can differ from passing a temporary: a temporary removed a 1-byte `lea` difference in house AI_Raise_Money.
- An explicit `Point3D(TClass->Lepton_Dimensions())` copy instead of `Coord dim = ...` changed register allocation to match (techno Draw_Pre_Render). It may stand for a different return type in the 1.001 header.
- Header-count effect, measured: adding a template member to vector.h with an out-of-class definition broke base Read_INI and wonline Pick_Lobby (4 bytes each). Defining the same member inline in the class restored Read_INI; Pick_Lobby stays a header-fragile WOL function (dropped_w5c.json).

## KEY: VC6 stack-slot assignment (2026-11-21)
Measured with scratch experiments (e1-e6 and the hover replica e5/v1-v8/w1-w3, in the fslot agent's scratchpad) and confirmed on hover Start_Of_Move (18 -> 0 bytes) and unit Assign_Destination (frame 0x70 -> 0x80, all slots equal).
- Lifetime decides sharing, and the lifetime is syntactic:
  - A named local that lives in memory (class object, address taken) occupies its slot for its whole enclosing BLOCK, from the block's start, not from its declaration or first use. Sibling blocks share (e1 fD, e4).
  - A temporary lives for its statement. Temporaries of different statements share one slot; named locals and temporaries do not share inside the same block (e4 fT1: the later temporaries never took the dead named slot).
  - A spilled scalar (int, bool) has real liveness and can share with anything.
- Dead stack-argument slots are offered first. A symbol takes one only if its lifetime starts after the argument's last use. For a named local that means its BLOCK must start after that use (e1 fE, e3 fR/fS).
  - hover Start_Of_Move: `cell` was declared in the same block as `Basic_Path(..., num)`, so it could not take the `num` slot and the Adjacent_Cell temporary took it instead. Making the code after the failed-path block the `else` block gives the 1.001 layout: cell in the argument slot. A bare `{ }` block and `if (ok) {...} else {fail}` give the same slots (w1-w3).
  - Declaration order, declaring at function scope, `Cell c; c = ...`, `Cell c(...)`, a const reference, and the form of the inline helper do NOT move anything (v1-v8).
- Order inside the frame: 4-byte objects below 12-byte ones (e2 fK/fL); within a size, more references means a lower offset (e1 fB, e3 fO/fP). Ties: memory objects by first use, lowest first (e2 fF/fG); spilled scalars the other way round, the earliest definition highest (e2 fM); a memory object goes below a spill of equal weight (e3 fN).
- An `&&` / `||` chain used directly as an `if` condition is split into branches, and the class temporaries of its operands share ONE slot. The same chain stored in a bool (`bool ok = a && b && c;`) is one full expression: each temporary gets its own slot (e6 fD: frame 0xc -> 0x24). Nested ifs and De Morgan forms behave like the plain if.
  - So "1.001 frame larger by N x sizeof(temp)" means a condition was stored in a local; "1.001 frame smaller" means we keep in one expression what 1.001 tests in an if or spreads over statements.
  - unit Assign_Destination: the four-term burrow test stored in `bool canburrow` gives the exact 0x80 frame and all slots. It also moved inline decisions in the earlier Teleporter block (COUNT rule), so the function is still open.
- Method for a slot near miss: list which values share each slot in 1.001. A named local in an argument slot or sharing with a sibling means a narrower block; temporaries that do not share mean one expression; a uniform shift means one extra non-sharing item.
- Data point from queue.cpp Print_CRCs (other agent): declaring pointer locals inside their loops instead of at function scope fixed almost every slot; names and declaration order had no effect. Same rule.
- `List.ID(x) == -1` is a virtual call. Where 1.001 has an inline search loop instead, use `!List.Is_In_List(x)`. This fixed house AI_Building (from 1090 bytes to 0). Other `ID(...) ==/!= -1` sites in m85 (2026-11-21): techno x2, planmgr x2, building x2, wave, msengine. Check the original at those sites for an inline loop.
- Flattened TU-local helpers (static inline functions present in the file but unused, e.g. anim `_Flat_Distance`/`_Direction`/`_Move_Coord`) are a strong hint: restore their calls (anim Flaming_Guy_AI).
- Pointer locals declared inside their loops, plus `continue` instead of a wrapping `if`, fixed the 11 KB queue Print_CRCs (see the stack-slot KEY section).
- Stack-slot refinements (slot2 agent, 2026-11-21):
  - If two operands of one `&&`/`||` chain land in DIFFERENT slots, the chain was a full expression stored in a bool. VC6 jump-threads `bool b = a && c; if (!b)` into the same branch shape. This gave the exact slot layout of building Draw_Extras.
  - The bool form can, however, hoist a common subexpression such as `&PrimaryFacing` to the start of the statement and change the registers of the statement before it.
  - When a scalar already sits in the right argument slot but the function still differs, the cause is register weight, not the slot (infantry Per_Cell_Process).

## KEY: VC6 register choice for temporaries (2026-11-21)
Status: PARTIAL. The four register near-miss groups (anim AI, map Damage_Low_Bridge*, cell Reduce_Tiberium / Place_Veins / Recalc_Attributes) are still open; no new match. What was measured (scratch: W/build/level2/reglab, tools try.sh / regress.py / mkvar.py / mut.py, lab files lab/e1-e4.cpp):
- Plain rule (lab e3 k1-k8, e4 k11/k12): for `a+b < c+d` with operands of equal weight, VC6 evaluates the RIGHT operand of the compare first. The first temporary takes the lowest free scratch register (eax, then ecx/edx, then callee-saved). Swapping the source sides swaps both the evaluation order and the registers, and turns `cmp l,r / jge` into `cmp / jle`. A heavier operand (memory load) goes before a lighter one (`lea reg+reg`). Declaration order of the locals has no effect.
- The Union near misses do NOT follow that plain rule, and that is the finding: reversing the two edge compares in rect.h (`rect2.X+rect2.Width > result.X+result.Width`) changes only the cmp/jcc direction in anim AI and Damage_Low_Bridge*; the registers stay with the operand's identity (result sum / rect2 sum). So these registers are not expression temporaries handed out during the tree walk. They are the global allocator's choice for the short live ranges of result.Width/Height and the cached rect2 field, and 1.001 simply has the two swapped (bridge: result.Width in ebp = its later home, rect2.Width in eax; ours the reverse. anim: rect2.Height in ebp, result sum in eax; ours the reverse).
- Reduce_Tiberium is the same thing one level up: 1.001 allocates result.X before result.Y (X takes ecx, so Y and Width cannot be coalesced with the destination registers and three extra `mov` appear); ours allocates Y first. The al/ecx swap in the `levels = OverlayData` branch is the same kind of order flip.
- rect.h Union is pinned. Eight body variants were run against all claims of anim, cell and map: copy-ctor form, declare-then-assign, field-wise ctor, early returns, rect2-first validity test, reversed compares: each breaks 1-12 matched functions (Reduce_Wall, Redraw_Veins, Place_Tiberium, Remove_Crate, Damage_Low_Bridge_Piece_*, ...). Neutral everywhere (no target fixed, no claim broken): non-const return type, commuted sums (`Width+X`). Removing the `T(...)` casts breaks Redraw_Veins: the casts count for the inline budget. Do not edit Union.
- Neutral in the callers (bytes unchanged): declaring overlayrect in an outer scope / before updaterect / in the loop, declare-then-assign, a named Union result, an int local for TacticalRect.Y (anim); swapped Union arguments, ctor form, for(;;) / while(true) instead of do-while(false), Top_Left() in the loop (bridge); early return, nested ifs, int tibtype, a separate result local, `Y = Y - ...`, declare-then-assign, an int local for OverlayData (Reduce_Tiberium). Everything else tried reshuffles the whole function (50-1900 bytes).
- Not the header-count effect: 1-40 extra extern/function/struct/typedef declarations in front of Reduce_Tiberium change nothing (the bridge functions were gauged earlier with the same result).
- Place_Veins lead refuted: seven other initialisations of adjrect (direct Union init, RECT_NONE, Rect temporary, declare + assign, field stores, declared outside the if) all change the function size (1952-2256 against 2192). `Rect adjrect(0,0,0,0)` plus assignment is the only form with the right size.
- Working hypothesis for the next attempt: the allocator orders candidates by a weight (use count times loop depth) and 1.001 has a different weight for one variable of the function, i.e. one more or one fewer use of a rect field or of `levels` somewhere else in the body. Look for a statement outside the Union that touches the same variable (a second read of draw_rect / updaterect / dirty, a different Register_Dirty_Area argument form), not at the Union statement itself.

## KEY: TU symbol-history dependence (2026-11-21, queue Print_CRCs)
- Some register and spill choices depend on how many local symbols VC6 compiled EARLIER in the same TU. The dependence is non-periodic and hash-like, not a simple count.
- Evidence: Print_CRCs (0x221b90) matches in the current queue.cpp. With the faithful 1.001 Wait_For_Players before it, Print_CRCs is 4-8 bytes off in its spill-reload order. A gauge of N dead int locals in Clean_DoList (between the two) matches only at N=10. Locals after Print_CRCs, and global declarations, have no effect.
- Consequence: a later function can match "by coincidence", compensating for unfaithful earlier functions. Make earlier functions faithful first, from string and disassembly evidence. NEVER fill the count with dead locals; that is a probe.
- Parked state: W/analysis/level2/parked/queue_r4/. queue_r4_scratch.cpp holds the faithful Wait_For_Players with Send_Port_Unreachable and Reset_Reconnect_Pings removed (1.006-only, no strings or gap in 1.001). chk.sh checks a copy against all claimed queue functions.

## KEY: VC6 aligned (and esp,-8) frames (2026-11-21)
Status: rule MEASURED in a lab; walk Movement_AI NOT solved, but the cause is narrowed down. Scratch: afr agent, scratchpad `walk/afr`, files e1-e20, generator `grid.py` + `lab.sh`. All lab functions are `void T::f(int a,int b)` members compiled with the level-2 flags and `-FAs`.

The decision compares a benefit score D with a fixed threshold and with a register cost C. It is absolute: 1280 extra int statements, calls or branches do not dilute it (e8, e16), and if-nesting, else branches, early returns and switch cases do not scale it (e14).

**Benefit D (aligned needs D >= 15).** Measured with two rulers (a double argument = 3, a local store plus one x87 use = 2), exact to the unit (e10, e12, e13, e15):
- 3 for every double ARGUMENT pushed, whatever its source and calling convention: `s1(a)` (fild/fstp [esp]), `s1(g0())`, `s1(1.5)` and `Set_Speed(0.0)` (two immediate pushes), `s1(member)`; virtual, thiscall, fastcall, cdecl and stdcall are all the same. Five such calls alone give an aligned frame (four: plain).
- 3 for every double assignment done as a memory COPY: `G = 0.0;`, `G = G2;`, `member = G2;`. Plus 2 for each side that is a stack double: `G = d;` and `s1(d)` are 5, a local-to-local copy `y = d;` is 7. Counted after CSE: `s2(d,d)` is 8, not 10; a hoisted load counts once.
- 1 for every x87 instruction that references a stack double: `fstp local`, `fld local`, `fadd/fmul [local]`, the load for `(int)d`. Eight `d = g0(); ... use d` pairs give alignment, seven do not (families SL, sd, ss).
- 0 for `fstp` to a global or member, for x87 arithmetic on globals or members, and for int-to-double conversions that stay on the x87 stack.
- A loop multiplies the weight: one `s1(i)` in a `for` loop is enough.
- Counted after tail merging: two source statements that VC6 cross-jumps into one call count once (walk variant u1: 9 or 10 `Set_Speed` statements, 8 emitted calls, same decision).
- Precondition: at least two stack-double items. One double argument plus any number of global copies never aligns (e12 row `OUT*GZ` n=1, e11 w2); two arguments plus three global copies do.

**Cost C (only when a stack PARAMETER is referenced in the body).**
- Without stack-parameter references VC6 keeps EBP as a normal callee-saved register INSIDE the aligned frame (`push ebp; mov ebp,esp; and esp,-8; sub esp,N; push ebx; push ebp; ...`). Then there is no register cost: the threshold stays 15 (18 with five or more candidates) under any register pressure (e18 rows `noa`, e19 rows `nob`).
- With a referenced stack parameter EBP is the parameter frame pointer and only ebx/esi/edi remain. Aligned then also needs D >= C, where C is the weight of the strongest register candidate that gets NO callee-saved register in the plain four-register allocation (the fifth candidate; with four or fewer candidates C = 0).
  - For a simple int local the weight is 2 x uses + 1. Measured thresholds: 8 uses -> 17-18, 10 -> 21, 11 -> 24, 15 -> 31, 20 -> 41 (e19, e20).
  - Further losers add roughly a fifth of their weight each (six equal candidates of 20 uses: 46-48; five losers of 10 uses: 37).
- The weights of the four winners do not matter (e19: 40/30/20/10 uses with a fifth of 5 uses stays at 15 whatever the others are). Oddity: the variable that really loses its register in the aligned build is the FOURTH, but the compiler prices the fifth.

**Consequences for source forms.**
- "Ours aligned, 1.001 plain" with identical x87 code means the cost side differs, not D. 1.001 has a heavier register candidate that stays in memory. Things that change C without changing the x87 code: more or fewer uses of a spilled int/pointer local or of a CSE temporary, a value kept in a named local versus recomputed, block scoping that changes which candidates conflict.
- "Ours plain, 1.001 aligned": look for a missing double copy (`double x = member;`, a double passed through a named local), a missing parameter reference, or a double argument that we fold away.
- D-neutral edits: reordering, nesting, early returns, extra int code. D-relevant: every double argument, and every named double local that is copied (5-7 each) instead of used directly by an x87 instruction (1 each).

**walk Movement_AI (0x312de0), measured with the rule.**

## KEY: VC6 symbol numbering and allocation order (2026-11-21)
Measured with `tools/level2_symgauge.py` (scratch: W/build/level2/symlab; reference sweeps q_loc, q_top, t_fire, t_gt, f_ai, h_ai, each with result.json).
- Hypothesis tested: "many slot-order and register-swap near misses come from VC6's internal symbol numbering". Result: REFUTED for those near misses; the numbering effect is real but rare and confined to one narrow pattern.
- The mechanism, as far as measured (queue Print_CRCs, parked r4 state):
  - VC6 gives every declaration a number from ONE TU-wide counter (the suffix in /FAs names: `_housep$102050`, `$T124345`, `$SG...`, `$L...`). Named symbols get theirs while the front end parses; the `$T` temporaries are numbered after the whole TU (124xxx against 101xxx).
  - The code of Print_CRCs depends on that counter with an exact period of 64 (N = 0..280 dead locals in Clean_DoList: digest(N) = digest(N+64) everywhere; matches at N = 21, 51, 85, 115, ...).
  - What changes is ONLY the order of two adjacent reloads at a loop bottom after a call (`mov eax,[_i$]` / `mov ebx,[_housep$]` against the reverse), at 4 independent sites. 4 sites = exactly 16 code variants, and every sweep shows the same 16. Slot offsets, registers and all other instructions are identical in all variants.
  - Units per item (fitted against the dead-local sweep): unused `extern int`, `static int`, typedef, local (dead or used), string literal = 1; function prototype = 2; empty function definition = 3; `struct { int a; }` = 9. Unused declarations DO count; names do not. A dead local moves named numbers by 1 and later `$T` numbers by 2.
  - The place matters, not just the total: 0..63 externs at the top of queue.cpp give matches at N = 9, 18, 19, 20, 25, 58; the same externs just before Clean_DoList give 21 and 51. So the hash involves numbers assigned throughout the TU (file statics, labels, temporaries), not one base offset of the function.
  - Not resolved: the hash itself. Ruled out: order by `number mod 64` of the two reloaded symbols, any fixed order on residues mod 64 (cyclic for every assumed number of `_i$`), and any linear hash `(c*n+b) mod 64`. The /FAs symbol list is sorted by `number mod 2048`, which is a different table.
- How rare: 64-step sweeps (unused externs in front of the function) leave these byte-for-byte UNCHANGED: techno Fire_At 0x2bfe50, techno Greatest_Threat 0x2bbb60, FootClass::AI 0xc8bf0, HouseClass::AI 0xe37a0, and every claimed function of techno.cpp (239), foot.cpp (151), house.cpp (276) and queue.cpp (45 of 46; only Print_CRCs moves). ## KEY: spilled-scalar slot order (w73, 2026-11-21, techno Fire_At)
Measured in a lab with esp-frame functions that keep 7-10 int locals live across calls. Files and lab.sh are in the w73 scratchpad (techno/w73/lab, t1-t3).
- Among spilled 4-byte scalars with equal weight, the slot order follows the END of the live range. The variable whose last use comes latest sits highest (nearest the frame top); the one that dies first sits lowest. Definition order and declaration order make no difference (t2 B2/B6, t3 C4).
  - Use counts decide WHICH variables get a register. They do not change the order of those that spill (t3 C5/C6).
  - The older note "earliest definition highest" (e2 fM) is a special case: there, definition order and death order coincided.
- Caveat from Fire_At 0x2bfe50: the final-code lifetimes are not the input. For every misplaced spilled scalar (weapon, object, firepower, bullet, max_speed, btype, valid_arc), the memory-reference spans are identical in ours and in 1.001: the same first and last instruction offsets and the same counts. Yet the slots differ.
  - So VC6 orders by pre-optimisation (IL) live ranges and weights. Two source forms that fold to the same code can still give different slots.
  - Replacing a source path with a CSE-equal local, for example `btype->ROT` instead of `weapon->Bullet->ROT`, changes the frame, and here also the code.
  - Declaration forms of the variable (const or not, declare-then-assign, position) stay neutral, as before.
- Inline decisions move whole slot groups. In Fire_At, calling Horizontal_Speed out of line inside the inlined Set_Pitch swapped the velocity and fire_coord slots and put object/speed into their 1.001 slots.
  - So settle the call list first (calls_hist identical), then look at slots.
- Practical method:
  1. Check calls_hist and the inline gauge (dead `Coord(1,2,3);` after the affected statement). Look for hand-flattened member calls: in Fire_At, `Electric_Zap(target)` (an overload defined earlier in the TU) and the `this != NULL && (AbstractFlags & 4)` cast pattern. Restore them; their call sites are the missing budget.
  2. Only then compare slots. For a remaining permutation with equal final spans, look for source references that the optimiser folds away (CSE'd member paths, redundant casts or copies). Do not look for different lifetimes in the final code.
- Refinements (w75, 2026-11-21, Fire_At 3775 -> 3763 bytes):
  - The frame is ONE ordered sequence of slot groups of all sizes. Doubles, 12-byte objects and 4-byte scalars interleave, and each group is placed at the next suitably aligned offset. A 4-byte hole in 1.001 directly above an 8-aligned double is alignment padding: a 4-byte scalar moved from above that double to below it. Read holes as "order changed", not as an extra variable.
  - Weight decides the order before the end of the live range does; heavier goes lower. One extra source use moves a group down: `btype->Create_Bullet` instead of `weapon->Bullet->Create_Bullet` put btype/segments below the -144 double. One fewer use moves it up (`weapon->Bullet->IsInaccurate`).
  - The weight belongs to the slot GROUP. Everything that shares the slot counts, including hidden-return temporaries. In Fire_At, the DirType temporary of `PrimaryFacing.Current()` inside `Set_Yaw(DirType(PrimaryFacing.Current().As_Radian() + offset))` shared the spilled `dir` slot. Naming it (`DirType facing = PrimaryFacing.Current();`) gives otherwise identical code: the temporary moves to the temporary group, the dir group gets lighter, and three groups take their 1.001 places (btype -148, valid_arc -149, velocity/fire_coord swapped). So a statement far from the misplaced variable can be the lever. Look for temporaries listed at the same offset as the spilled scalar (`$Tnnn = -144` next to `_dir$`).
  - Uses are counted after inlining, forward substitution and CSE. Neutral (no byte or slot change): a TU-local inline wrapper that carries the uses through its parameter, a named `bullet->Class` local for three CSE'd reads, declaring bullet or max_speed at function top, extra if-nesting around the uses.
  - Spill weight includes the reloads that register allocation creates. 1.001's weapon has a 4th reference (a reload after the inlined Electric_Zap, whose locals get ebx). That is why it sits lower. This is a register decision for the region, and in Fire_At it reacts only to the DENSE use statement after the branch: removing 3 of the 4 `weapon->` arguments of the later Set_Bullet_Data flips it, while 3 scattered condition uses do not. Before hunting for slot forms of such a variable, compare its reload count with 1.001's.

## Compiler flags context (2026-11-22, EA Renegade VC6 projects; renegade_vc6_flags.md)

## Lessons from gibbo101/ra2-decomp docs/AGENTS.md (@719fcc7, 2026-11-22; credited in SOURCES_CREDITS.md)
- **Count of named, initialised locals.** Register and slot ties can follow the COUNT of named, initialised locals: sometimes modulo 8, sometimes by which run of eight it falls in.
  - Names, places and scopes do not matter. Uninitialised locals, named references and address-taken locals do not count.
  - Fix it with a real named value the code already computes: a local per call argument, a named element pointer per loop body, a local copy of a global, or an expression split into steps.
  - This fixed Region_Threat and Generate_Starting_Points for us, and closed 11 of 47 contributed matches for gibbo. Their tools/localprobe.py sweeps the count, as a diagnostic.
- **Inline budget from the end backwards.** VC6 spends the inline budget from the END of the function backwards, latest call first. Code after a call reduces that call's budget, and every inlined call costs the same. This is consistent with our COUNT rule.
- **Switch layout.**
  - Case bodies are laid out group by group: runs of case values dispatched together, ascending, and in source order within a group. Moving whole groups changes which call sites get inlined.
  - Shared `break` code goes after the LAST case that breaks into it.
  - Of identical return tails, VC6 keeps the one reached by a taken jump over the fall-through ones. This is relevant for our tail-placement near misses: Match_Start_Game, WOL_Game_Setup_Dialog_Proc, OnPublicGameOptions.
- **Naming a call's result in its own statement** moves that call ahead of the other arguments' loads, which fixes argument-order and register swaps.
- **A tiny auto-inline never fails the budget.** A very small auto-inline (a null test plus an accessor) never fails the budget, at any depth. If 1.001 calls one out of line, look for another cause.
- **Frame offsets for big frames.** In frames over 128 bytes, `/Z7` plus the S_BPREL32 records in .debug$S show every local's frame offset.
- **Declaration weights** for heap- or hash-sensitive matches (our symbol-numbering issue):
  - 1 per variable, typedef or forward declaration;
  - 2 per enum;
  - 1 plus the parameter count per function declaration;
  - 3 per inline definition;
  - 8 plus the member count per class.
  - Redeclarations and #defines weigh nothing.
  - Use this to reason about hash-order victims (Print_CRCs, Trackbar_Proc) once a TU is complete.
- **NDEBUG.** gibbo builds files whose asserts are compiled out with `#define NDEBUG` before the includes (ownrdraw, wonline).
- **Tested 2026-11-22 (localcount agent): the local-count lever is NOT a general explanation for our register and slot near misses.**
  - Flat probe curves over K=0..40 for OnUserList, Handle_User_Leave, Locale_Dialog_Proc and house AI.
  - Single thresholds only for Create_Game_Channel (K=11), Do_MISSION_MISSILE (K=20) and Draw_Extras (a band of about 6 at +0x53e).
  - Run `tools/level2_localprobe.py` first, about a minute per function, before trying named-local rewrites.
  - What counts: declare-then-assign counts like initialised; never-assigned locals do not; named objects (Point2D) do.
  - Draw_Extras: do not change its named-local count without rechecking +0x53e.

## F13: the SIGN of an inline unit is the number of assignment statements in its expansion (threshold 3); ctor forms as natural units (2026-11-22, missile Projectile_Motion 0x190670, not matched)
- Answer to F8's open question (40 probe types, agents/f13_missile/cal2.py + pre.h). An inline call site weighs by how many ASSIGNMENT statements its expansion creates: member initializers, stores in the body, and the parameter temporaries that a NESTED inline needs when its arguments are converted. Expression size, nesting depth and narrowing by themselves do not count.
  - 1 or 2 assignments: about -1.5 (the site only makes the caller bigger: MORE inlining later). Examples: `N1(int) : a(x)`, `M3(int,int) : a(x), b(y)`, `TPoint2D<short>(1,2)`, Point2D(1,2), a `(short,short)` derived ctor, a body `a = x; b = y;` with int->short narrowing.
  - 3 or more: positive (LESS inlining later): 3 stores about +1 (`: a(x), b(x), c(x)` with ONE parameter +1.5), 4 about +1.5, 6 about +2..2.5. The jump from 2 to 3 is about 2.5 units.
  - Every extra argument, and every non-constant argument (a member load), is about -0.5.
  - Inlines without assignments (`return x + x + x + x + x + x;`, an if/return, empty void) stay at -0.5..-1 whatever their size.
- Why F8's two probes were positive: `Cell(int,int) : BASECLASS(x, y)` passes int parameters to the (short,short) base ctor, so the expansion has 2 conversion temporaries + 2 stores = 4 assignments; `TPoint3D<int>(x,y,z)` has 3 stores. A clone with a (short,short) signature flips to -1.5.
- So "N more positive units with identical code" means: some inline used in the function has a form with 3+ assignment statements where ours has 1-2. The cheapest such forms are constructor forms: a mem-initializer list `: BASECLASS(v), Z(v.Z)` is 2 statements, the body form `{ BASECLASS::operator = (v); Z = v.Z; }` is 3 (default base ctor + assignment + store) and compiles to the same bytes. Each use of that ctor is worth about +2/3 of a unit here (3 copy sites = +2).
- A converting ctor moves conversions out of the caller: `target_direction = TVelocity3D<double>(delta);` with `TVelocity3D(TPoint3D<int> const & pt) : BASECLASS(TVelocity2D<T>(pt.X, pt.Y)), Z(pt.Z)` is +2 units against `TVelocity3D<double>(delta.X, delta.Y, delta.Z)` (three member-load arguments become one reference), keeps the 2D temporary, and moves the Z `fild` behind the base copy exactly as 1.001 has it. Rule: when the int->double loads of a (x,y,z) construction are scheduled later than ours, test a ctor that takes the whole point.
- Result for Projectile_Motion: with these three velocity.h forms (agents/f13_missile/proposal_e1_hdr.json; INFERRED, not applied, needs hdrcheck over all velocity.h users) the gauge need drops from 6..8 to 1..3 sites and the function is at 66 bytes / 8 instructions with all 8 controls. ## L1 library binding: lessons (2026-11-23, agent L1; tool W/analysis/level2/agents/l1_lib/l1_bind.py, report.md there)
- A masked section match is a position, not a name. Bind first: build a name -> address table from sections that are already certain (existing entries, patterns unique in the whole .text), then accept another section only where a trusted reference names its symbol, or where it is the only masked position whose operands all agree with the table.
- libident's contiguity and section-order inference was wrong in 7 of 133 cases: memcpy/memmove (0x36ebd0 is `_memmove`, 0x3745e0 is `_memcpy`), `__matherr`/`___init_collate`, the cprintf/woutput `_get_int64_arg` pair, and `??1__non_rtti_object`. Never take a twin's name from placement.
- Static twins (`_write_multi_char`, `_strncnt`, `_fix_grouping`, `_get_int_arg`) are decided by the static call from their own member's uniquely placed section.
- Vtables and function tables are callers too: once code fixes a data section's base, its relocations name the deleting destructors and init functions they point at.
- An IAT check by name fails for DLLs imported by ordinal (OLEAUT32). Compare the ordinal with the VC6 import library (level2_check.lib_import_ordinal); that recovered 4 comsupp.obj sections (1439 bytes) libident had dropped.
- A library COMDAT can be emitted by a game TU (std::ctype<unsigned short>::id initialiser at 0xfcf0): the first definition wins, so it is not library-linked code. Keep library entries inside the CRT tail.
- LIBC.LIB names are wrong for this LIBCMT image where the MT build splits a function: the body at 0x36e02b is `__fread_lk`, and `_fread` is the locking wrapper at 0x36dffc (same for `_fwrite`, `__getch`, `__getche`, `__kbhit`, `__ungetch`, `__putch`).
- Search cost: a lookahead regex per section over the whole .text is fine for about 150 sections (13 s); a fixpoint that restarts after every acceptance and evaluates thousands of positions of 1-byte sections is not. Derive candidate positions from the references instead.
- metadata/level2_functions.json can be mid-rewrite when read; retry a JSON parse error once before reporting it.
